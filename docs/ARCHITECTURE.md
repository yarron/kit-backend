# Архитектура: что выбрано и почему

Документ не про «как правильно вообще». Он про решения, проверенные на боевых
проектах, и про то, **при каких условиях каждое решение перестаёт работать**.
Правило без границ применимости — это карго-культ.

---

## 1. Выбор базы данных

Начинай не с «какая база лучше», а с одного вопроса:

> **Нужны ли мне транзакции между несколькими таблицами и жёсткая схема?**

```
                   ┌─ да ──────────────► PostgreSQL + Prisma
Нужен ли мне SQL? ─┤
                   └─ нет ─────────────► MongoDB + Mongoose

Отдельно, поверх любого из них:
данные только ДОПИСЫВАЮТСЯ и читаются агрегатами? ──► ClickHouse
```

### MongoDB + Mongoose — дефолт, когда SQL не нужен

Берём, когда данные документные, схема ещё движется, а межтабличных
транзакций нет. Разработка заметно быстрее: не надо гонять миграции на каждое
поле.

**Почему Mongoose, а не Prisma или TypeORM для Mongo:**

- **Prisma** для MongoDB — гражданин второго сорта. Она проектировалась под
  реляционку; часть возможностей Mongo (полноценный aggregation pipeline,
  вложенные структуры произвольной глубины, точечные операторы обновления) либо
  недоступна, либо доступна через сырой доступ — то есть в обход того самого
  слоя, ради которого Prisma и бралась.
- **TypeORM** для Mongo поддерживается по остаточному принципу и медленнее.
- **Mongoose** — нативный для Mongo инструмент: aggregation, populate,
  middleware, discriminators работают как задумано, а не «почти».

Плюс конкретно для NestJS: `@Schema`/`@Prop` и `@ObjectType`/`@Field` живут на
одном классе (см. `src/modules/user/user.entity.ts`), и новое поле добавляется
в одном месте.

**Когда Mongo — ошибка:** деньги с межсчётной проводкой, отчётность, требующая
JOIN'ов по пяти таблицам, жёсткие внешние ключи. Мультидокументные транзакции
в Mongo есть, но они дороже и требуют replica set — если ты о них думаешь
постоянно, тебе нужен Postgres.

### PostgreSQL + Prisma — когда SQL действительно нужен

Транзакции, внешние ключи, сложные JOIN'ы. Prisma даёт типобезопасный клиент,
внятные миграции и хороший DX.

**TypeORM больше не берём.** Медленнее во всём: и в разработке (сырые edge-кейсы
и неочевидное поведение), и в рантайме. Legacy-проекты на нём живут; новые
на нём не начинаются.

### ClickHouse — третья база, а не замена первым двум

Берётся под другой профиль нагрузки: строки **только дописываются** и читаются
**агрегатами** по большому объёму. Логи, события, метрики, история сделок.

Правило: **текущее СОСТОЯНИЕ — в Mongo/Postgres, неизменяемая ИСТОРИЯ — в
ClickHouse.** В стартере это `orders` (состояние) и `order_event` (история).

Чего ClickHouse не умеет, и это надо принять до, а не после:
- **нет UPDATE и нет уникальных ограничений.** `ReplacingMergeTree` схлопывает
  дубликаты по ключу — но **на фоновом merge**, когда решит. Пока не схлопнул,
  `SELECT` вернёт обе строки. Отсюда `FINAL` в каждом чтении (см.
  `analytics.service.ts`) и версия в каждой строке;
- **нет транзакций**;
- **ненавидит мелкие INSERT'ы.** Каждый — отдельный part на диске; на большом
  потоке сервер умирает на `too many parts`. Отсюда `async_insert` — батчит
  сервер, а не приложение.

ClickHouse может быть частью бэкенда (как здесь) или отдельным сервисом. Выносят
не «потому что аналитика», а когда у неё другая нагрузка и она начинает мешать
основному API.

### Две базы в одном приложении — нормально

Mongo для состояния + ClickHouse для истории — уже две. Mongo + Postgres в одном
сервисе тоже встречается: например, документная основная модель и отдельный
реляционный биллинг, где нужны транзакции. Это не «плохая архитектура», это
осознанный выбор инструмента под задачу.

## 2. Очереди: Redis + BullMQ

**Берём Redis, а не Kafka/RabbitMQ/NATS.** Причина простая: Redis почти всегда
уже есть в проекте (кэш, сессии, rate limit), а BullMQ поверх него закрывает
всё, что реально нужно 95% проектов:

- ретраи с экспоненциальным backoff,
- отложенные задачи (`delay`),
- приоритеты,
- повторяющиеся задачи,
- дедупликация по `jobId`,
- **BullBoard** — веб-интерфейс на `/que`, где видно очереди, упавшие job'ы,
  их payload и стектрейс, и откуда можно перезапустить руками. Это то, что
  превращает отладку фоновой обработки из гадания в чтение.

Kafka даёт то, чего у BullMQ нет: переигрывание истории (log retention),
разделение на партиции с гарантией порядка, сотни тысяч сообщений в секунду,
несколько независимых групп потребителей одного потока. Если ни одно из этого
не нужно по имени — Kafka это лишний кластер, который надо кому-то
эксплуатировать.

**Признак, что Redis перестал хватать:** нужно переиграть события за прошлую
неделю; или нужен строгий порядок внутри ключа при нескольких потребителях;
или объём такой, что Redis не держит.

## 3. GraphQL code-first

Схема генерируется из TypeScript-классов. Альтернатива (schema-first: пишешь
`.graphql`, генеришь типы) даёт два артефакта, которые расходятся.

Что обязательно, а не по вкусу:

- **`depthLimit`.** GraphQL позволяет запросить `user { orders { user { … } } }`
  бесконечно. Без ограничения глубины один запрос кладёт сервер;
- **introspection и playground выключены в проде.** Это полная карта модели
  данных;
- **общий `FilterGetInput`** вместо отдельного input-типа на каждую сущность:
  таблица на фронте пишется один раз и работает со всеми коллекциями. Плата —
  имена колонок приходят строками, поэтому сервис **обязан** сверять их с
  белым списком (`GraphqlMongooseService.allowedColumns`). Иначе клиент
  фильтрует по полям, которых ты не собирался показывать.

## 4. Когда выносить микросервис

Не «когда проект большой». Когда выполнено хотя бы одно:

1. **Модуль независим по данным** — не ходит в чужие таблицы, общается
   событиями.
2. **У него другой профиль нагрузки** — например, CPU-тяжёлая генерация
   отчётов, которая на общем инстансе душит API.
3. **Ему нужен свой цикл релизов** или своё масштабирование.

Если ничего из этого нет — это модуль внутри монолита, и вынос добавит сетевые
вызовы, распределённые ошибки и деплой на два сервиса вместо одного.

**Язык нового сервиса:** по умолчанию тот же NestJS — общий код, общие подходы,
один набор навыков в команде. **Go** берут, когда упёрлись в железо: очень
высокая нагрузка при жёстком бюджете на память/CPU. Это редко и на специфичных
задачах (биржи, шлюзы, high-throughput прокси). Не начинай с Go «на всякий
случай» — начни с профилировщика.

## 5. Инструменты гигиены

| инструмент | зачем |
|---|---|
| **Biome** | линт + формат в одном, на порядок быстрее ESLint+Prettier. Один конфиг вместо трёх |
| **only-allow pnpm** | падает на `npm install`. Смешанные lock-файлы = «у меня работает» |
| **prebuild: pnpm check** | нельзя собрать неотформатированный код. Проверка, которую можно забыть, не проверка |
| **env-cmd + профили** | `LOCAL` / `TEST` / `PROD` в одном файле. Никаких «а какой .env сейчас активен» |
| **Sentry** | трейсы из прода с source maps. Загрузка карт — шаг сборки, иначе стектрейс из минифицированного кода бесполезен |
| **Terminus healthcheck** | проверяет ЗАВИСИМОСТИ. Процесс жив, а Mongo недоступна — платформа обязана это увидеть |

## 6. Хостинг: Railway

После опыта с GCP, AWS и прочими — для проектов такого масштаба выбор
**Railway**. Причина не в моде:

- любая инфраструктура (Postgres, Mongo, Redis, ClickHouse, S3-совместимый
  бакет) поднимается за минуты, без терраформа и без отдельной роли DevOps;
- деплой из GitHub-репозитория, окружения (staging/prod) — это копия проекта,
  а не отдельный ад конфигураций;
- предсказуемая цена по фактическому потреблению;
- логи и метрики из коробки.

Что нужно знать заранее:

- **приватная сеть** между сервисами — используй внутренние адреса, а не
  публичные: это быстрее и не тарифицируется как внешний трафик;
- **volume обязателен** для БД: без него данные живут до передеплоя;
- **`startCommand` не любит экранирование.** Если надо положить конфиг-файл при
  старте — только через base64, иначе парсер съест бэкслеши и сервис ляжет;
- **healthcheck** должен отвечать раньше, чем прогреются тяжёлые зависимости,
  иначе платформа перезапустит контейнер до того, как он поднимется.

AWS/GCP берут, когда действительно нужны их специфические сервисы или когда
этого требует комплаенс. Для остального они — сложность, которую кто-то должен
обслуживать.
